Define your short links, analytics <Terminology title="background analytics integration on a link" to="/docs/reference/terminology#tracker">trackers</Terminology>, private app access, and <Terminology title="edge function that serves your redirects" to="/docs/reference/terminology#cloudflare-worker">worker</Terminology> settings through a single JSON configuration file managed by the CLI.

## Config File Location

The CLI resolves `config.json` by checking these locations in order:

1. Current working directory
2. Project root (detected by `package.json`)
3. User config directory (`~/.config/branded-short-links/`)

If no <Terminology title="the config.json deployment settings file" to="/docs/reference/terminology#config">config</Terminology> file exists, the CLI copies the starter template bundled with the npm package into the user config directory.

## Structure

The <Terminology title="the config.json deployment settings file" to="/docs/reference/terminology#config">config</Terminology> file has three required top-level sections and one optional `app_access` section:

```json title="config.json"
{
  "links": { ... },
  "trackers": [ ... ],
  "app_access": { ... },
  "settings": { ... }
}
```

## Settings

Controls <Terminology title="edge function that serves your redirects" to="/docs/reference/terminology#cloudflare-worker">worker</Terminology> identity and debug behavior.

| Field                  | Type      | Required | Description                                                  |
|------------------------|:---------:|----------|--------------------------------------------------------------|
| `worker_name`          | `string`  |    Yes   | Name of the <Terminology title="edge function that serves your redirects" to="/docs/reference/terminology#cloudflare-worker">Cloudflare Worker</Terminology> deployment. |
| `base_domain`          | `string`  |    Yes   | <Terminology title="domain your shortcodes live on" to="/docs/reference/terminology#base-domain">Base domain</Terminology> for short links (e.g., `example.com`). |
| `show_response_output` | `boolean` |    Yes   | Show masked <Terminology title="the config.json deployment settings file" to="/docs/reference/terminology#config">config</Terminology> on the <Terminology title="branded page served at the root" to="/docs/reference/terminology#landing-page">landing</Terminology> and <Terminology title="page shown when nothing else matches" to="/docs/reference/terminology#404-page">404</Terminology> pages for debugging. |

```json title="config.json"
{
  "settings": {
    "worker_name": "branded-short-links",
    "base_domain": "example.com",
    "show_response_output": false
  }
}
```

## Links

Defines the <Terminology title="path segment that maps to a URL" to="/docs/reference/terminology#shortcode">shortcode</Terminology>-to-URL mappings and an optional <Terminology title="redirect used when no shortcode matches" to="/docs/reference/terminology#fallback-url">fallback</Terminology>.

| Field          | Type     | Required | Description                                               |
|----------------|:--------:|----------|-----------------------------------------------------------|
| `fallback_url` | `string` |    No    | Default redirect for unmatched <Terminology title="path segment that maps to a URL" to="/docs/reference/terminology#shortcode">shortcodes</Terminology>. Must be a valid URL. |
| `items`        | `array`  |    Yes   | Array of <Terminology title="single shortcode-to-URL config entry" to="/docs/reference/terminology#link-item">link items</Terminology> (see below). |

### Link Item

Each <Terminology title="single shortcode-to-URL config entry" to="/docs/reference/terminology#link-item">item</Terminology> maps a <Terminology title="path segment that maps to a URL" to="/docs/reference/terminology#shortcode">shortcode</Terminology> path to a destination URL with a specific redirect status.

| Field           | Type     | Required | Description                                                    |
|-----------------|:--------:|----------|----------------------------------------------------------------|
| `shortcode`     | `string` |    Yes   | Path segment starting with `/` (e.g., `/github`). Min 2 chars. |
| `http_response` | `number` |    Yes   | HTTP redirect status: `301`, `302`, `303`, `307`, or `308`.    |
| `redirect_url`  | `string` |    Yes   | Destination URL. Must be a valid URL.                          |

```json title="config.json"
{
  "links": {
    "fallback_url": "https://example.com",
    "items": [
      {
        "shortcode": "/github",
        "http_response": 301,
        "redirect_url": "https://github.com/yourname"
      },
      {
        "shortcode": "/linkedin",
        "http_response": 302,
        "redirect_url": "https://linkedin.com/in/yourname"
      }
    ]
  }
}
```

### Redirect Status Codes

| Code  | Name               | Use Case                                                 |
|-------|--------------------|----------------------------------------------------------|
| `301` | Moved Permanently  | Permanent redirect. Search engines transfer link equity. |
| `302` | Found              | Temporary redirect. Original URL retains SEO value.      |
| `303` | See Other          | Redirect after POST. Forces GET on the destination.      |
| `307` | Temporary Redirect | Temporary redirect. Preserves the original HTTP method.  |
| `308` | Permanent Redirect | Permanent redirect. Preserves the original HTTP method.  |

### Shortcode Matching

The <Terminology title="edge function that serves your redirects" to="/docs/reference/terminology#cloudflare-worker">worker</Terminology> strips trailing slashes before matching. Query strings and hash fragments are not used for matching and are not forwarded to the redirect destination for matched <Terminology title="path segment that maps to a URL" to="/docs/reference/terminology#shortcode">shortcodes</Terminology> — the redirect always goes to the exact `redirect_url` from your <Terminology title="the config.json deployment settings file" to="/docs/reference/terminology#config">config</Terminology>.

This differs from <Terminology title="redirect used when no shortcode matches" to="/docs/reference/terminology#fallback-url">fallback</Terminology> redirects, which do preserve the original path, query, and hash (see below).

| Request                                  | Matched Shortcode | Redirect Destination                                                                                                                                                                                                                                                |
|------------------------------------------|-------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `https://example.com/github`             | `/github`         | `https://github.com/yourname`                                                                                                                                                                                                                                       |
| `https://example.com/github?ref=twitter` | `/github`         | `https://github.com/yourname`                                                                                                                                                                                                                                       |
| `https://example.com/github/`            | `/github`         | `https://github.com/yourname`                                                                                                                                                                                                                                       |
| `https://example.com/unknown`            | (none)            | <Terminology title="redirect used when no shortcode matches" to="/docs/reference/terminology#fallback-url">Fallback URL</Terminology> or <Terminology title="page shown when nothing else matches" to="/docs/reference/terminology#404-page">404 page</Terminology> |

### Fallback URL Behavior

When a request doesn't match any <Terminology title="path segment that maps to a URL" to="/docs/reference/terminology#shortcode">shortcode</Terminology> and a `fallback_url` is configured, the redirect behavior depends on the request path:

- **Root path (`/`)** — Redirects to the <Terminology title="redirect used when no shortcode matches" to="/docs/reference/terminology#fallback-url">fallback URL</Terminology>'s origin only (e.g., `https://example.com`). The original path, query string, and hash are not forwarded.
- **Any other path** — Redirects to the <Terminology title="redirect used when no shortcode matches" to="/docs/reference/terminology#fallback-url">fallback URL</Terminology>'s origin with the original pathname, query string, and hash fragment preserved (e.g., `/about?ref=home#section` appended to the <Terminology title="redirect used when no shortcode matches" to="/docs/reference/terminology#fallback-url">fallback</Terminology> origin).

<Terminology title="redirect used when no shortcode matches" to="/docs/reference/terminology#fallback-url">Fallback</Terminology> redirects always use HTTP status `301` (Moved Permanently). This is not configurable — only <Terminology title="path segment that maps to a URL" to="/docs/reference/terminology#shortcode">shortcode</Terminology> redirects use the per-link `http_response` setting.

When no `fallback_url` is configured, the root path serves the <Terminology title="branded page served at the root" to="/docs/reference/terminology#landing-page">landing page</Terminology> and all other unmatched paths serve a <Terminology title="page shown when nothing else matches" to="/docs/reference/terminology#404-page">404 page</Terminology>.

## Trackers

An array of analytics integrations. Each <Terminology title="background analytics integration on a link" to="/docs/reference/terminology#tracker">tracker</Terminology> has a `type` field that determines which additional fields are required. All <Terminology title="background analytics integration on a link" to="/docs/reference/terminology#tracker">trackers</Terminology> fire in parallel on every matched <Terminology title="path segment that maps to a URL" to="/docs/reference/terminology#shortcode">shortcode</Terminology> redirect.

See [Trackers](/docs/configuration/trackers/) for the full reference on each <Terminology title="background analytics integration on a link" to="/docs/reference/terminology#tracker">tracker</Terminology> type.

### Quick Reference

| Type                 | Required Fields                        |
|----------------------|----------------------------------------|
| `ga4`                | `name`, `measurement_id`, `api_secret` |
| `facebook`           | `name`, `pixel_id`                     |
| `ntfy`               | `name`, `server`, `topic`, `token`     |
| `ntfy-reverse-proxy` | `name`, `url`; optional: `token`       |
| `posthog`            | `name`, `host`, `api_key`              |
| `plain-text`         | `name`, `url`; optional: `token`       |

## App Access

The optional `app_access` section enables the private read-only endpoint at `https://<base_domain>/__bsl/links`. A native client signs in with the deployment URL, a configured username, and its <Terminology title="deployer-managed credential for the private app API" to="/docs/reference/terminology#access-key">access key</Terminology> over HTTPS Basic authentication.

```json title="config.json"
{
  "app_access": {
    "users": [
      {
        "username": "jacky",
        "access_key": "artist-cactus-forest-magnet-river"
      }
    ]
  }
}
```

| Field        | Type     | Required | Description |
|--------------|:--------:|----------|-------------|
| `users`      | `array`  | Yes      | Deployer-managed app users. An empty array keeps the endpoint disabled. |
| `username`   | `string` | Yes      | Unique lowercase username using letters, digits, periods, underscores, or hyphens. |
| `access_key` | `string` | Yes      | Key generated by `bsl access add` or `bsl access rotate`. |

The CLI supports three cryptographically random key formats:

| Format      | Shape                      | Best For                                                            |
|-------------|----------------------------|---------------------------------------------------------------------|
| `memorable` | Five lowercase words       | Manual entry on another device.                                     |
| `compact`   | Five four-character chunks | Shorter manual entry using unambiguous Crockford Base32 characters. |
| `random`    | `bsl_` plus 43 characters  | Copy and paste when manual entry is not needed.                     |

Credentials are intentionally stored as plain text in `config.json` because the app is read-only and configuration changes require a redeploy. Keep the config private. The authenticated response includes branded URLs, redirect destinations, response codes, fallback URL, and tracker configuration, but never includes the `app_access` section. Public landing and 404 debug output also omit the entire section.

## Sample Config

The full sample configuration file:

```json title="config.json"
{
  "links": {
    "fallback_url": "https://example.com",
    "items": [
      {
        "shortcode": "/example",
        "http_response": 301,
        "redirect_url": "https://example.com/destination"
      }
    ]
  },
  "trackers": [
    {
      "name": "my-ga4",
      "type": "ga4",
      "measurement_id": "",
      "api_secret": ""
    }
  ],
  "app_access": {
    "users": []
  },
  "settings": {
    "worker_name": "branded-short-links",
    "base_domain": "example.com",
    "show_response_output": false
  }
}
```

## Validation

Run the validate command to check your <Terminology title="the config.json deployment settings file" to="/docs/reference/terminology#config">config</Terminology> against the schema:

```bash
bsl validate
```

Validation checks:

- All required fields are present and correctly typed.
- URLs are valid format.
- <Terminology title="path segment that maps to a URL" to="/docs/reference/terminology#shortcode">Shortcodes</Terminology> start with `/` and are at least 2 characters.
- HTTP response codes are one of the allowed values.
- No duplicate <Terminology title="path segment that maps to a URL" to="/docs/reference/terminology#shortcode">shortcodes</Terminology> exist.
- No duplicate <Terminology title="background analytics integration on a link" to="/docs/reference/terminology#tracker">tracker</Terminology> names exist.
- No duplicate app-access usernames exist.
- The reserved `/__bsl/links` path is not used as a <Terminology title="path segment that maps to a URL" to="/docs/reference/terminology#shortcode">shortcode</Terminology>.
- App usernames and <Terminology title="deployer-managed credential for the private app API" to="/docs/reference/terminology#access-key">access keys</Terminology> match their supported formats.
- <Terminology title="background analytics integration on a link" to="/docs/reference/terminology#tracker">Tracker</Terminology>-specific fields match the declared type (extra fields are rejected).

## Environment Variables

The CLI resolves `.env` by checking these locations in order (same as <Terminology title="the config.json deployment settings file" to="/docs/reference/terminology#config">config</Terminology> resolution):

1. Current working directory
2. Project root (detected by `package.json`)
3. User config directory (`~/.config/branded-short-links/`)

The first `.env` file found is loaded automatically. During first deploy, the CLI saves new <Terminology title="Cloudflare credential authorizing CLI deployments" to="/docs/reference/terminology#api-token">tokens</Terminology> to `~/.config/branded-short-links/.env`.

| Variable               | Purpose                                                                                                                                                                                                                                                                                                     |
|------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `CLOUDFLARE_API_TOKEN` | <Terminology title="Cloudflare credential authorizing CLI deployments" to="/docs/reference/terminology#api-token">API token</Terminology> for <Terminology title="edge function that serves your redirects" to="/docs/reference/terminology#cloudflare-worker">Cloudflare Workers</Terminology> deployment. |
| `NODE_ENV`             | Node.js environment setting.                                                                                                                                                                                                                                                                                |
| `LOG_LEVEL`            | Controls CLI log verbosity.                                                                                                                                                                                                                                                                                 |
| `LOG_TIME`             | Enables timestamps in CLI log output.                                                                                                                                                                                                                                                                       |
